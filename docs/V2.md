# Peregrine — Version 2 plan

Features agreed for v2. Nothing here is built yet; this is the spec to implement
from. Everything must hold Peregrine's invariants: local-first, BYO model, the
egress guard + Activity Log for anything that leaves the machine, and
**profession-neutral** — every feature works for a nurse, teacher, or tradesperson,
not just engineers.

---

## 1. Assistant modes — Senior / Thinker / Companion / Helper

Today there's one persona ("Senior <profession> mode"). v2 turns that single sidebar
card into a **live switcher** across four modes. Each mode is a different *stance* —
the voice and behavior change, the grounding and no-invention rules never do. All
four stay shaped by the user's profession and seniority.

| Mode | Stance | Sounds like | Best for |
|------|--------|-------------|----------|
| **Senior** *(current)* | Seasoned mentor: direction, critique, standards | "Here's how I'd structure it — and the trap most hit first." | leveling up, honest critique |
| **Thinker** | Reasons *with* you: questions, options, tradeoffs, devil's advocate | "What's the one constraint everything else bends around?" | decisions, strategy, untangling |
| **Companion** | Warmth + momentum: support, celebrates wins, gentle accountability | "That stuck feeling is normal — let's find one small step." | rough days, accountability |
| **Helper** | Pure execution: minimal talk, hands back the artifact fast | "On it — here's a draft you can edit." | churning through tasks |

### Behavior
- Each mode is a **system-prompt layer** on top of the existing profession/seniority prompt.
- The mode is **global** (one active mode app-wide), swapped from the sidebar switcher; choice **persists in the vault** (new `chat_mode` setting).
- Applies to the **senior chat** first; the **debrief** inherits it. Meetings and résumé stay task-focused regardless.

### Auto-suggest (opt-out, never automatic)
- When the conversation clearly fits another mode, Peregrine surfaces a **one-line chip** in the chat — e.g. "Sounds like a heavy one — switch to Companion?" with **Yes / not now**. It only *offers*; the user flips it.
- **Rare and quiet:** at most one nudge per stretch, dismissible, backs off when declined — no repeating, no counter, nothing boss-facing (avoids the surveillance/nagging failure mode of tools like 15Five).
- **Detection** is done by the model itself (it already sees the conversation) — a tired/frustrated tone → Companion, a big fork → Thinker, "just draft it" → Helper. No new tracking; nothing stored beyond the user's choice.
- **Off switch:** a single "suggest modes for me" toggle in Settings, on by default.

### Build surface
- 4 prompt templates; `chat_mode` in `settings.rs`; sidebar card → switcher component; the suggest chip in the chat; the Settings toggle.

## 2. News ingestion & synthesis — a role-aware briefing

A four-stage service that turns a professional news feed into a short, ranked set of
"why this matters to *you*" cards. Adapted to Peregrine's Rust/local-first stack
(the original spec named the Python `google-news-feed` library; we fetch and parse
the feed directly in Rust instead).

### Stage 1 — Fetch
- Build a query from the user's **profile keywords** (profession + a new user-editable "interests" list — e.g. a nurse's "critical care, patient safety, nurse staffing"; an engineer's "DevOps, Kubernetes, Terraform"). Never hard-code engineer terms.
- Hit the **Google News RSS search endpoint**:
  `https://news.google.com/rss/search?q=<keywords>%20when:7d&hl=<lang>&gl=<country>&ceid=<country>:<lang>`
  - `when:7d` = recency window (configurable).
  - `hl` / `gl` / `ceid` = locale, from settings (default from OS locale).
- Fetch with `reqwest` (already a dep) through the **egress guard**, and record it in the **Activity Log** — this is a new outbound host (`news.google.com`); it must be transparent and respect trust mode (in **Airtight**, the briefing is disabled — no non-local traffic).
- Parse the RSS XML in Rust (add a small parser: `rss` or `quick-xml`/`feed-rs`).
- **Resolve redirect links:** Google News items link to `news.google.com` redirects. v1 resolves each to its real article URL by following the redirect (HEAD/GET, capture the final URL). Note the extra request per item; cache aggressively (Stage 4).
- Only the keyword query leaves the machine here — no vault data. Still, disclose it.

### Stage 2 — Dedup & filter
- Feed items carry: title, link, publish date, description, source.
- **Group near-identical stories** from multiple outlets into one item (title similarity — e.g. normalized token overlap / Jaccard over a threshold).
- **Drop** anything older than the window, or below a **relevance threshold** scored against the user's profile keywords (keyword overlap in title+description; keep it cheap and local — no model call in this stage).

### Stage 3 — Synthesize
- For each survivor, send **title + description only** (never the full article body in v1 — sidesteps paywalls/blocking) to the user's **chosen model** via the existing `model::send` egress-guarded path.
- Prompt produces: a **short professional summary** (one paragraph) + **one "why it matters to someone in this role" line**, grounded strictly in the provided text, no invention.
- Keep it profession-aware via the same `{profession}`/`{seniority}` context.

### Stage 4 — Deliver
- Return a **ranked list of cards**: title, one-paragraph summary, why-it-matters line, source name, resolved link.
- Ranking: relevance score (Stage 2) × recency.
- **Cache per user for a few hours** (store the synthesized cards + a fetched-at timestamp in the vault or a local cache file; serve from cache within the TTL) so scrolling doesn't re-hit the feed or re-summarize. Manual "refresh" allowed.
- New **Briefing** screen (or a card on Today); clicking a card opens the resolved link via the opener plugin.

### Build surface
- Rust: `news_fetch` (RSS + resolve), `news_dedup`/relevance (local), `news_synthesize` (model), a cache keyed by keyword-set+locale with TTL. Settings: interests list, locale, window, enable toggle. Frontend: Briefing screen + cards.

### Open questions
- Where to surface it — a dedicated **Briefing** screen, or fold into Today / a morning brief?
- Relevance scoring: keep it purely local (keyword overlap) in v1, or allow an optional model re-rank?
- Redirect resolution cost — accept one request per item in v1, or lazy-resolve only when a card is opened?
